# SoundCanvas 升级方向调研

调研日期：2026-11-02。优先目标：技术深度、作品集和职业发展，同时寻找真实使用场景。

本报告依据本地代码、在线演示的六种效果、竞品官方资料和两项相关研究。竞品功能与价格为公开页面信息，未逐一实测；没有开展用户访谈、销量调查或跨设备性能测试。以下方向排序是基于这些资料的判断，不代表已经验证市场需求。本轮只新增调研文档。

## 1. 建议选择的方向

**把 SoundCanvas 做成可编排的音乐视觉乐器，以“音乐逐渐长成一件声音雕塑”为第一件代表作品。**

目标使用者先限定为独立音乐人、创意编程爱好者和需要短段视觉素材的创作者。一次完整使用是：导入自己的音乐 → 看见具有音乐关系的视觉生成 → 调整少量映射 → 保存作品或导出短片。潜在复用理由是为下一首作品重新创作，而不是为了再次浏览同样的六个效果。

项目应有一个一分钟内能看懂的展示，也应有能展开讲二十分钟的工程内容：音乐事件提取、具有时间尺度的映射、GPU 图形、统一时间轴、可重放状态，以及实际用户比较。不要同时做完整 VJ 软件、视频剪辑平台和音乐分析研究系统。

这不是一个尚无竞争的新品类。机会在于做出自己的视觉语言和清楚、可靠的创作体验；“浏览器里能跟音乐动”本身已经不足以区分项目。

## 2. 现有项目真正值得继承的部分

六个效果分别是 Retro Spectrum、Wave Pattern、Needles、Dancing Earth、Groove、Torus Knot。在线演示可以播放内置音乐并切换效果。它已经包含频域、时域、频段能量、历史积累和三维参数曲面几种思路。

值得延续的三项资产：

- **快／中／慢响应和残影。** `filter.js`、`arrayfilter.js` 已经在探索视觉的时间行为。可以将它发展为可解释、可调节的响应系统，例如力度、起落速度、余韵和记忆长度。
- **Groove 的声音记忆。** 音乐播放过的历史变成唱片纹路，比单纯随瞬时音量缩放更有叙事空间。适合发展为螺旋、年轮、地形、雕塑等持续生长的作品。
- **Torus Knot 的程序化几何。** 已经有沿曲线生成管状曲面的实现，可以进一步研究几何、材质、光照与声音之间的分工，而不是只增加更多形状。

从代码看，需要跨过的边界也很明确：

| 当前实现 | 升级时需要回答的问题 |
| --- | --- |
| `sketch.js:14` 固定加载一首 FLAC | 别人的音乐怎样进入？README 提到实时输入，但当前代码没有实现麦克风或文件选择入口 |
| `controlsAndInput.js` 用数字键切换，空格显示菜单 | 首次访问者是否能发现功能，并完成自己的作品？ |
| `vis/torusknot.js:24` 等处使用 `millis()` | 暂停、跳转、重放、导出时，画面应该对应哪一个音乐时刻？ |
| `Filter.update()` 随绘制调用推进 | 帧率改变、效果切走再切回时，响应时间和历史状态如何保持一致？ |
| `Groove.update()` 每个时间槽记录 `wave[0]` | 如何把示意性的纹路变成稳定、可复现、有音乐含义的历史特征？ |

尤其要区分：目前 Groove 的纹路不是完整音频波形刻录，也不应宣传为歌曲的唯一指纹；它取的是波形窗口的第一个采样值，并写入约每秒 30 个时间槽。未来可改为固定音频窗口的响度、频段能量、瞬态等摘要。

当前滤波也主要是在跨画面调用的特征／波形位置上做处理，不等同于以固定音频采样率处理连续音频。升级时应明确滤波对象与更新频率。这是一个很好的工程研究入口，而不只是重构理由。

作为价格量级参照，Synesthesia 官网列出的 Standard 为 $199、Pro 为 $399；这说明成熟工具会围绕专业工作流收费，不构成市场规模或新项目收入预测。[官方价格](https://synesthesia.live/pricing)

这些资料共同支持的判断是：可视化数量很难成为你的优势。更值得投入的是音乐关系、创作控制、独特美术，以及输出的可靠性。这个判断不意味着竞品做不好这些事情。

## 4. 三条可选路线及排序

以下比较是针对本项目和当前优先目标的主观判断。

| 路线 | 具体产物 | 最能证明的能力 | 主要代价 | 建议 |
| --- | --- | --- | --- | --- |
| A. 可编排的音乐视觉乐器 | 声音特征驱动视觉参数，支持调整、保存和重放 | 图形、音频、交互和系统设计结合 | 容易膨胀成复杂编辑器 | **主方向**；第一版只做少量映射 |
| B. 歌曲生成声音雕塑 | 将一段音乐积累成可浏览的螺旋、地形或三维物件 | 程序化几何、视觉设计、时间数据表达 | 漂亮但可能只体验一次 | **作为 A 的第一件代表作品**；先验证音乐人是否愿意用于自己的作品 |
| C. 面向音乐人的发行视觉工具 | 导入音乐与封面，生成可发布短片 | 产品完成度、媒体工程、创作者工作流 | 模板、剪辑、格式、商业竞争会占用大量时间 | 如果以后优先考虑产品收入，再重点转向 |

不建议把多人同步、VR、手势、完整节点编辑器、生成式视频全部并进。它们可能做出好项目，但目前没有足够理由证明比主方向更值得先做。

## 5. 技术深度应该放在哪里

### 5.1 音乐驱动需要有多个时间尺度

先做可测量的基本特征：响度、频段能量、声音起音／瞬态，以及节拍估计。让不同特征承担不同视觉职责，而不是所有东西一起随低音缩放。

- 毫秒到短时：瞬态触发局部冲击，响度影响形变幅度。
- 节拍尺度：节拍相位组织运动，频谱变化改变表面纹理。
- 较长时间：能量趋势影响整体生长或场景密度。
- 歌曲段落：后续加入候选分段，允许人工修正，不把变化检测直接宣称为准确理解主歌／副歌。

对低置信度节拍估计，应能切到连续能量驱动或人工节拍。电子舞曲、自由速度钢琴、环境音乐不应被强行套进同一种节奏模型。预录文件可以预分析未来片段；实时输入不能无延迟地预知下一次高潮，产品承诺必须区分。

浏览器音频分析有现成基础，例如 [Essentia.js](https://github.com/MTG/essentia.js) 通过 WebAssembly 提供音乐／音频分析能力。现阶段应把它视为待评估候选，而不是预先决定依赖；接入还需要核对性能、接口和项目许可。

### 5.2 把滤波经验变成用户可理解的映射系统

最小表达可以是“声音来源 → 响应方式 → 视觉属性”：例如“低频能量 → 快起慢落 → 雕塑厚度”。用户能看到当前值、改变强度、反转方向，并保存配置。

前台先提供三个能听懂的控制，如冲击、余韵、生长；需要时再展开频段、范围、平滑等细节。不要一开始要求用户理解一整张信号处理图。

2021 年一项音频驱动可视化系统研究发现，参与者认可同步与表现力，但也遇到音频特征术语和技术问题。其可用性评分并不高。这支持把“映射是否易懂”作为需要验证的设计问题，而不是仅增加技术控制。[研究原文](https://arxiv.org/abs/2106.10134)

### 5.3 用统一时间轴保证重放和导出

把音频时间、视觉状态和控制事件联系起来，让相同音频、配置、随机种子和事件记录能重放出一致的作品。状态型效果需要固定步长推进，并考虑跳转时重建状态或使用检查点；仅替换 `millis()` 不足以解决全部问题。

用户获得的价值是：调好的结果可以保存，跳回某一段不会完全变样，导出接近预览。作品集可以展示的深度则是：时钟、状态管理、缓存、误差和复现机制。

[Web Audio 规范](https://www.w3.org/TR/webaudio/)提供音频处理与时间相关基础；[WebCodecs 规范](https://www.w3.org/TR/webcodecs/)提供编码接口。它们不自动解决完整导出流程：仍需处理音画时间戳、容器封装、内存和设备编码支持。初版先支持一个明确的桌面浏览器和一种短片规格，再扩展。

### 5.4 图形效果应有明确的研究问题

选择一个代表场景，研究怎样用声音改变几何、材质和时间演化。可以从 Torus Knot 延伸到带有历史层次的声音雕塑：整体轮廓表达长期变化，局部褶皱表达瞬态，材质表现高频活跃度；这些都是艺术映射，没有普适的“音色对应颜色”真值。

性能优化应该有测量依据。现有曲面在绘制中计算许多几何表达式，值得检查 CPU 成本，但尚未测量，不能认定它就是瓶颈。先固定设备、分辨率和片段，记录帧时间，再决定预计算、缓存、GPU 顶点形变或其他方案。

可以保留 p5.js 作为旧版对照或原型层。是否迁移渲染方案，应由需要的效果和测量决定；换框架或使用 WebGPU 本身不能证明作品价值。

## 6. 第一版应当长什么样

推荐的演示流程：

1. 默认提供一段可公开演示的音乐，打开即能理解作品。
2. 用户导入自己的本地音频，系统显示处理进度。
3. 音乐逐渐形成一件声音雕塑，可以在时间轴上回看。
4. 用户调整冲击、余韵和生长三个控制，立即看见区别。
5. 展开一个简单映射面板，理解“这个动作来自什么声音”。
6. 保存配置，并导出一段 15–30 秒的短片。

第一版优先预录文件，实时麦克风放到第二阶段；这样可以先解决可重复的分析与编排。首版只需一个视觉做得足够好，再加频谱作为解释与对照。原有六种可保留为历史展示。

暂不加入登录、付费、社交动态、模板市场、全功能剪辑、复杂多人协作、完整投影映射。短期没有证据表明它们能提高这个代表作的说服力。

也不宜依赖 Spotify 接入来定义首版。Spotify 官方平台文档明确限制将其录音与视觉媒体同步；本地音频导入能减少平台依赖。这里的判断针对通过 Spotify 平台访问的内容，不把它泛化为所有音频采集场景。[Spotify 官方说明](https://developer.spotify.com/documentation/web-api/reference/get-information-about-the-users-current-playback)

## 7. 怎样证明它真的变好了

只展示“现在更漂亮”很难支撑技术深度。建议保留三个对照：原来的直接特征映射、新的多时间尺度映射、新映射加用户控制。比较时尽量保持相同场景和美术，避免把视觉风格差异误当成算法效果。

| 要回答的问题 | 建议的证据 |
| --- | --- |
| 画面是否更贴合音乐？ | 选择电子、原声／自由速度、环境三类片段，随机展示 A/B，收集偏好与理由；另用人工标注起音片段检查同步 |
| 用户是否真的能创作？ | 先招募约 5–8 位目标用户，用自己的音乐完成导入、调整、保存或导出，记录卡点与是否需要帮助 |
| 是否具有复用价值？ | 邀请一周后用第二首音乐再做一次；记录实际回来的人和原因，不能只问“你会不会再用” |
| 是否稳定？ | 在注明型号、系统、浏览器与分辨率的设备上记录帧时间分布、处理耗时、内存和导出成功情况 |
| 是否可重放？ | 比较顺序播放、时间跳转和离线导出的关键帧；定义几何／参数一致性及容许的图像差异 |

可以将“未经指导约三分钟做出愿意保存的结果”“指定设备上 1080p 的 p95 帧时间低于 16.7ms”等设为探索性目标，必须注明它们是拟定目标，不是已经实现的结果。小样本可以揭示可用性问题，不能证明大规模市场需求或统计普遍性。

2025 年 musicolors 的定性研究指出，音乐可视化的使用价值还包括音乐构思、与其他系统集成，以及视听欣赏。这给“让人拿去创作”的方向提供支持，但没有验证 SoundCanvas 的具体方案。[研究原文](https://arxiv.org/abs/2503.14220)

## 8. 建议的推进顺序与作品集材料

按可停止、可判断的阶段推进，先不承诺工期；总耗时会受到每周投入和图形／音频基础影响。

1. **证明视觉身份。** 用三段风格不同的音乐做一个声音雕塑原型。必须先回答：换歌后的差异是否可感知、视觉是否有记忆点。
2. **证明音乐关系。** 加入固定更新率的特征和响应系统，与旧版比较；检查低音量、静音和无明显节拍情况。
3. **证明创作闭环。** 做本地导入、三个控制、配置保存、短片导出。让真实用户完成自己的作品。
4. **证明工程质量。** 完成时间轴重放、性能测量和技术文章；只有出现实际性能需要时再做更深的 GPU 优化。

如果前三种音乐做出来都像相同的待机动画，先回到映射与视觉语言；如果用户只围观、没人想保存自己的结果，先调整场景或定位，暂缓扩建编辑器。

最终作品集至少包含：可在线体验的成品、60–90 秒展示视频、旧版与新版的受控比较、一篇解释关键取舍和失败情况的技术文章，以及测试者实际做出的几件作品。可以用一张小架构图展示音频分析、映射、渲染、时间轴和导出的关系。

不同职业方向可以调整深挖比例：前端／创意工程偏重交互和性能；图形偏重 GPU 管线和几何；音频／多媒体偏重特征、时序与评估；HCI 偏重映射可理解性和创作研究。不要为了覆盖所有职位而扩大第一版。

最终应当能够拿证据说出：**我把一个六种效果的课程项目，做成了能让别人用自己的音乐创作、调整并可靠输出作品的浏览器工具，并验证了它在什么情况下比旧版更好。**
